# ВышКат — учёт парка кикшеринга

ДЗ №1 по КПО. Java 17, Maven, Guice (DI), JUnit 5, JaCoCo.

## Запуск

Открыть проект в IntelliJ IDEA (через `pom.xml`) и запустить `ru.hse.vyshkat.Main`.

Тесты: `mvn test`, отчёт о покрытии появится в `target/site/jacoco/index.html` (сейчас около 90% строк).

## Что есть в программе

Меню:
1. Добавить транспорт — сначала проходит техосмотр, если не прошёл, в парк не попадает
2. Поставить вещь на баланс (шлем, док-станция)
3. Количество транспорта/вещей и суммарное суточное потребление энергии
4. Транспорт для новичков (простота ≥ 6)
5. Инвентарная ведомость: номера и названия всего, что на балансе
6. Загрузить демо-данные (там есть два самоката, которые не пройдут техосмотр)

Если ввести буквы вместо числа, число не из диапазона, пустую строку или занятый номер — программа переспрашивает.

## Структура

- `domain` — модель:
  - интерфейсы `InventoryItem` (инвентарный номер и название) и `EnergyConsumer` (суточный расход)
  - `Vehicle` → `ElectricScooter`, `Bicycle`, `ElectricBike`
  - `Equipment` → `Helmet`, `DockStation`
- `service` — `ServiceCenter` (интерфейс техосмотра) и `SimpleServiceCenter`, `BeginnerPolicy` (правило для новичков)
  и `SimplicityBeginnerPolicy`, `Park` (учёт)
- `di/AppModule` — привязки Guice
- `console/ConsoleApp` — меню

Интерфейсы разделены, потому что номер есть у всего, а энергию тратит не всё: велосипед и шлем
`EnergyConsumer` не реализуют, а не возвращают 0.

Правила техосмотра (`SimpleServiceCenter`): пробег не больше 5000 км, у электротранспорта расход не больше 1.5 кВт·ч в сутки.

Правило для новичков вынесено в `BeginnerPolicy`, потому что в ТЗ сказано, что его будут усложнять.
Сейчас там базовое правило (простота ≥ 6), новое правило — это новый класс и одна строчка в `AppModule`.

## Ответы на вопросы

**1. Какой принцип SOLID применён наиболее явно?**
DIP: `Park` зависит от интерфейсов `ServiceCenter` и `BeginnerPolicy`, а какие реализации подставятся, решает `AppModule`.
В тестах вместо настоящего техосмотра и правила передаются лямбды.

**2. Какой принцип почти нарушен?**
OCP в `ConsoleApp`: при новом виде транспорта нужно дописать ветку в `addVehicle()`. Решил, что для консоли
это нормально — место одно, а `Park` и техосмотр менять не придётся. Ещё поле расхода повторяется
в `ElectricScooter`, `ElectricBike` и `DockStation` — отдельный общий класс ради одного поля не делал.

**3. Что будет при расширении?**
- Новый вид транспорта — новый класс-наследник `Vehicle` + пункт в меню. `Park` и техосмотр не меняются.
- Сотрудники — номера у них нет, поэтому это отдельный класс, не `InventoryItem`, в `Park` не попадает.
- Склад запчастей — тоже отдельный класс, запчасти считаются количеством, а не по номерам.

**4. Какие тесты проверяют техосмотр и правило для новичков?**
- `SimpleServiceCenterTest` — границы 5000/5001 км и 1.5/1.51 кВт·ч.
- `SimplicityBeginnerPolicyTest` — граница правила: простота 6 подходит, 5 нет.
- `ParkTest` — с лямбдой вместо техосмотра: прошёл → в парке, не прошёл → нет; правило для новичков
  тоже подменяется лямбдой (например, «только велосипеды»).
- `AppModuleTest` — техосмотр подменяется прямо в контейнере через `Modules.override`.
